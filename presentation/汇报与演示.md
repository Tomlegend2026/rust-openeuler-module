# 汇报讲稿与演示顺序

建议10分钟，由六人分段讲。下列技术说明可直接用于准备汇报；凡涉及“运行成功”都须在实测后才能表达。尚未完成时如实展示当前状态，不能把预期日志作为真实截图。

## A 开场与目标 约1分钟

“我们负责的是任务2：学习 Rust，并编写能在 openEuler 中动态加载和卸载的内核模块。我们选择了一个数据统计模块作为最小实例。它的价值在于完整展示初始化、状态保存、错误处理和资源释放，而不仅是打印一句 Hello World。整个项目从环境、实现、测试到复现都有对应记录。”

展示 README 和目录。用一句话解释动态装卸：系统运行中加入和移除模块，不必为每次操作重启。

## B 环境与版本 约1分钟

“模块必须对应实际运行的内核。我们选定 openEuler 源码提交与对应工具链，检查 Rust、模块和卸载配置，再完整构建和启动实验内核。”

展示实际版本表、uname 与 kernelrelease。若尚未运行，不说“我们成功启动”，而是指出待验证项。

## C 构建过程 约1分钟

“学习程序使用 Cargo，内核模块使用 Kbuild。Kbuild 提供目标内核的配置、符号和 Rust 支持代码。我们的脚本先检查环境，再生成 .ko，并记录模块信息和校验值。”

展示 Kbuild、Makefile、真实构建日志与 modinfo。解释为什么只安装 rustc 不够。

## D Rust 实现 约2分钟

“加载入口创建六个整数，使用 try_push 处理可能的分配失败。统计函数借用只读切片，不拿走数据所有权。成功后，向量移动进模块实例，一直保留到卸载。Drop 先输出状态，随后字段析构释放向量。我们特意把日志命名为 unload_begin，避免把进入 Drop 误说成释放已经完成。”

展示 rust_team2.rs 与 statistics.rs。指出 checked_add 和空输入错误。说明默认数据预期总和23，算法边界由主机测试覆盖。

## E 现场演示 约3分钟

先检查自己使用正确 VM，且没有同名模块。终端一执行 `sudo dmesg -w`。终端二依次：

```sh
uname -r
modinfo module/rust_team2.ko
sudo insmod module/rust_team2.ko
lsmod | grep '^rust_team2 '
sudo rmmod rust_team2
lsmod | grep '^rust_team2 '
```

解释第二次 grep 无匹配是预期结果。随后展示此前真实10轮日志，也可以在现场再次运行：

```sh
sudo bash scripts/test-lifecycle.sh module/rust_team2.ko 10
```

若失败，不临时升级整个环境；保留错误，展示同版本真实录屏并说明。没有录屏就明确失败原因和已完成部分。

## F 结论与限制 约2分钟

“Rust 的所有权、借用、Result 和 Drop 让资源归属和清理路径更明确。但安全 Rust 不能自动保证整个内核没有缺陷。主机逻辑测试与内核装卸测试覆盖的内容不同，我们分别记录。下一步若增加字符设备等接口，还需要考虑注册撤销、并发访问和失败回滚。”

展示实际贡献表和引用来源。结论只总结已验证结果。

## 全员答辩卡

- 问：为什么不能用 cargo build 生成这个内核模块？答：内核依赖目标配置和符号、定制的 Rust 构建环境，由 Kbuild 提供。
- 问：values 为什么不会在 init 结束时释放？答：成功时所有权移动进模块实例。
- 问：初始化中途分配失败怎么办？答：? 返回错误，局部已取得资源按作用域析构，模块不会进入成功加载状态。
- 问：Drop 中日志出现就证明无泄漏吗？答：不能；日志先于字段析构，且有限测试不能排除所有泄漏。
- 问：纯算法测试通过等于内核实验通过吗？答：不等于，后者还需要真实构建和运行证据。
- 问：能直接用其他内核版本吗？答：需要重新核对 API、工具链、配置和 ABI，再构建复测。
