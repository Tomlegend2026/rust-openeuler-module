# 模块如何工作

## 1 用户态与内核态

普通 Rust 程序运行于用户态，通常使用 std 和 Cargo。它不能直接代替内核模块。内核模块的机器代码加载进内核地址空间，与内核共享执行环境。本项目由目标内核 Kbuild 构建，构建参数施加 no_std，使用内核提供的 kernel crate 和适配的分配设施。

`insmod` 是用户态工具，通过模块加载系统调用请求内核解析模块、解析符号并运行初始化入口。`lsmod` 展示内核当前模块信息。`rmmod` 请求内核移除模块；满足卸载条件后内核触发模块清理。

## 2 module! 与 init

module/rust_team2.rs 中的 module! 宏登记模块类型、名称、作者、说明和 GPL 许可。宏负责生成该目标内核要求的胶水代码。固定源码的初始化签名是 `fn init(_module: &'static ThisModule) -> Result<Self>`。

初始化先建立一个空 Vec，再用 try_push 放入六个数字。每次分配可能失败，`?` 将错误返回给内核；成功时将数据移动进模块实例。因为初始化完成前数据仍由局部变量持有，中途失败时已经取得的向量资源会随局部变量析构，不需要手写 free。

## 3 统计逻辑与借用

statistics.rs 的 summarize 接收 `&[u64]`：它临时借用数据，只读，不取得所有权。返回 Statistics，包含 count、sum、min、max。对空数据返回 EmptyInput；使用 checked_add 防止溢出，失败返回 SumOverflow，而不是依赖 panic。

默认 `[3,1,4,1,5,9]` 的统计值为6、23、1、9。内核入口将统计错误映射为 EINVAL。当前固定输入不触发这两个错误；对应主机测试只证明纯算法边界，不表示已在内核注入分配失败。

## 4 模块为什么保存数据

RustTeam2 有两个字段：values 持有向量分配，summary 持有统计值。`Ok(Self { values, summary })` 把所有权交给模块实例，使数据在模块加载期间存活，而不是初始化函数结束就消失。

## 5 Drop 与卸载

卸载时内核的 Rust 模块胶水销毁该实例，先执行自定义 Drop::drop。它输出保留元素数和总和。随后 Rust 自动析构各字段，Vec 的析构负责释放其拥有的缓冲区。

因此日志名称是 unload_begin。日志能证明执行进入 Drop，不能单凭这行证明释放已完成，也不能证明所有可能的泄漏都不存在。rmmod 返回成功和模块列表消失提供另外的生命周期证据。

## 6 Rust 帮助了什么

所有权让数据只有明确的负责者；共享借用限制统计函数修改原数组；Result 把正常可恢复错误表达成返回值；Drop 将资源生命周期和类型绑定。本组代码没有手写 unsafe，但内核 Rust 抽象内部仍有底层不安全操作，且逻辑错误、错误的内核配置或内核本身的缺陷仍然可能造成问题。

## 7 为什么要固定版本

Rust 内核 API 仍随源码演化。本初稿核对的 openEuler 提交使用 author 字段、Vec::try_push 和当前 init 签名；其他版本可能不同。编译器、绑定生成器、内核配置、导出符号和运行内核共同影响 `.ko` 是否可加载。仅看到“Linux 6.6”还不足以认定所有产物兼容。

## 8 与参考示例的关系

模块入口框架采用官方最小 Rust 示例的惯用结构，出处和许可见 THIRD_PARTY_NOTICES.md。本初稿新增独立统计逻辑、边界测试、稳定日志字段、构建检查与循环验证。不要把参考框架声称为本组原创发明。
